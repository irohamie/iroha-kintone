# Phase 4：デプロイ手順の確立（検証用アプリのみ）

**ここから初めてkintoneへの書き込みが発生します。対象は検証用アプリのみです。**
本番アプリには絶対に触らないこと。

## 前提の確認（あなたがやること）

作業前に以下をまーくんに確認してください。

1. 「Phase 2 の初回バックアップは完了・コミット済みですか」
   （`git log` で確認できるので、あなたが調べて報告してもよい）
2. 「検証用アプリ `テスト_GitHub連携検証` は作成済みですか。アプリIDを教えてください」

検証用アプリが未作成の場合、以下をボタン単位で案内する。

1. kintoneのポータル画面で「アプリをつくる」をタップ
2. 「はじめから作成」を選ぶ
3. アプリ名に `テスト_GitHub連携検証` と入力
4. 適当な文字列フィールドを1つ配置して「アプリを作成」をタップ
5. 作成後、画面右上の歯車マーク →「設定」タブ →「JavaScript / CSSでカスタマイズ」を開く
6. 「PC用のJavaScriptファイル」に短いテスト用JSを2つアップロードする
   （順序の維持を検証するため必ず2つ以上）
7. 画面右下の「保存」をタップ
8. 画面右上の「アプリを更新」をタップ
9. 歯車マーク →「設定」タブ →「アクセス権」の「アプリ」をタップ
10. `GitHub連携（自動）` を追加し、「アプリ管理」のチェックボックスだけをオンにする
11. 「保存」→「アプリを更新」をタップ
12. URLの `?app=` の後ろの数字（アプリID）をまーくんに確認してもらう

アプリIDを受け取ったら、`node scripts/02_list_apps.js` を実行して
`config/apps.json` に登録し、`enabled: true`、`note` に `検証用・本番運用なし` を設定する。

## 作るファイル1：scripts/04_preflight.js

引数：`--app={アプリID}`

1. `GET /k/v1/app/customize.json?app={id}`（運用環境）を取得
2. `GET /k/v1/preview/app/customize.json?app={id}`（テスト環境）を取得
3. 両者を比較する
   - `scope` が一致するか
   - 4配列それぞれについて、要素数・順序・`type`・`name`・`url`・`size` が一致するか
   - `fileKey` は比較対象に含めない（アップロードごとに変わるため）
4. 完全一致なら「未反映の変更なし。デプロイ可」と表示し終了コード0
5. 不一致なら差分内容を日本語で具体的に表示し、
   「他者による未反映の変更があるため中止します。kintoneのアプリ設定画面を確認してください」
   と表示して終了コード1

【禁止】書き込み系APIを呼ぶこと

## 作るファイル2：scripts/05_snapshot_before.js

引数：`--app={アプリID}`

1. `04_preflight.js` のロジックを内部で呼び、失敗したら中止（Gate 1）
2. 運用環境の現行コードを `03_pull_all.js` と同じロジックで取得
   （size検証とMD5計算を必ず含める）
3. `_backup_before/{YYYYMMDD}_{folder}/` に保存する
   - `manifest.json` も含める
   - サブフォルダ構成は本体フォルダと同じ（`desktop/js` など）
   - `settings/` 配下のアプリ設定JSONも一緒に退避する
4. 同名フォルダが既に存在する場合は `_2` `_3` と連番を付ける
   【絶対禁止】既存フォルダを上書き・削除すること
5. `git add` してコミット・push
   メッセージ：`デプロイ前退避：{アプリ名}（App{ID}） {YYYY-MM-DD}`
6. 保存パス、ファイル名、バイト数、MD5の一覧を表示
7. push が失敗した場合は終了コード1で終わる（後続のデプロイを絶対に行わせないため）

## 作るファイル3：scripts/06_push_preview.js

引数：`--app={アプリID} --source={フォルダパス} [--allow-remove]`

1. Gate 1：preflight を内部実行。失敗なら中止
2. Gate 2：`_backup_before/` に当日日付のスナップショットが存在するか確認。
   無ければ「デプロイ前退避が未実施です。05_snapshot_before.js を先に実行してください」
   と表示して中止
3. `--source` の `manifest.json` を読み、送信ファイル一覧と順序を組み立てる
4. Gate 4：全JSファイルに `node --check` を実行。1つでも失敗なら中止
5. Gate 3：現行本番のファイル総数と送信ファイル総数を比較。
   送信数が少ない場合、`--allow-remove` が無ければ
   「ファイル数が {現行} から {送信} に減ります。意図的な削除であれば
   --allow-remove を付けて再実行してください」と表示して中止
6. 各ファイルを `POST /k/v1/file.json` で再アップロードし fileKey を得る
   （既存 fileKey の再利用はしない。CLAUDE.md 6-5 参照）
7. `PUT /k/v1/preview/app/customize.json` を送信
   - `app` / `scope` / `desktop` / `mobile` / `revision` をすべて明示
   - 4配列すべてを manifest の `order` どおりに完全列挙
   - 【禁止】`revision` に `-1` を指定すること
8. Gate 6：`GET /k/v1/preview/app/customize.json` で再取得し、
   各 FILE を `file.json` でダウンロードして MD5 を再計算。
   送信前と1つでも不一致ならエラーを報告して終了コード1
9. 送信前後のファイル名・バイト数・MD5の対照表を表示
10. 最後に「テスト環境への反映が完了しました。運用環境はまだ変わっていません。
    kintoneのアプリ設定画面で目視確認してください」と表示

【絶対禁止】`deploy.json` を呼ぶこと（このスクリプトはテスト環境までで止まる）
【絶対禁止】`revision` に `-1` を指定すること

## 作るファイル4：scripts/07_deploy.js

引数：`--app={アプリID} --confirm={アプリID} --summary={変更内容の日本語1〜2文}`

【重要】`--summary` は必須。人が判断できるのは「技術的な正しさ」ではなく
「これは自分が頼んだ内容と合っているか」だけであるため、承認前に必ず
平易な日本語サマリを提示すること（CLAUDE.md 7-3-1 参照）。

1. Gate 5：`--confirm` の値が `--app` と完全一致するか確認。
   不一致なら「確認用アプリIDが一致しません」と表示して中止
2. Gate 2：当日の `_backup_before/` スナップショットの存在を確認。
   さらに `git status` で未コミットの変更が無いことを確認
3. **承認待ちに入る前に、以下の形式で `$GITHUB_STEP_SUMMARY` に書き出す**
   ```
   【今回の変更】App{ID}（{アプリ名}）
   変更内容：{--summary の内容}
   ファイル数：{現行本番のファイル数}個 → {送信予定のファイル数}個（削除：{あり/なし}）
   退避済み：_backup_before/{当日}_{folder}/（問題があればここへ即座に戻せます）
   ```
4. `POST /k/v1/preview/app/deploy.json` を送信
   - body: `{ apps: [{ app: "{id}", revision: "{取得済みrevision}" }] }`
   - 【禁止】`revision` に `-1` を指定すること
5. `GET /k/v1/preview/app/deploy.json?apps[0].app={id}` を
   3秒間隔で最大20回ポーリングし、`status` が `SUCCESS` になるまで待つ
   - `PROCESSING` なら継続
   - `FAIL` または `CANCEL` なら即座に内容を表示して終了コード1
   - 20回超でタイムアウトとして報告
6. Gate 7：運用環境 `GET /k/v1/app/customize.json` を取得し、
   各 FILE をダウンロードして MD5 を再計算。送信前と照合
   - 一致：成功として報告
   - 不一致：「運用環境の内容が想定と一致しません。
     `_backup_before/{当日}_{folder}/` を `--source` に指定して
     06_push_preview.js と 07_deploy.js を再実行すれば元に戻せます」
     と復旧手順を明示して終了コード1
7. `_deploy_log/{YYYYMMDD_HHMMSS}_App{ID}.md` に以下を記録する
   - 実行日時（日本時間）／対象アプリIDとアプリ名／送信元フォルダパス
   - **`--summary` の内容**（後から「何のために変更したか」を追える記録として残す）
   - 退避先スナップショットのパス
   - 送信前後の全ファイルの名前・バイト数・MD5
   - deploy の status 推移／Gate 7 の照合結果
8. `_deploy_log/` をコミット・push
   メッセージ：`デプロイ記録：{アプリ名}（App{ID}） {YYYY-MM-DD HH:MM}`

【絶対禁止】preflight や Gate 2 をスキップすること
【絶対禁止】`revision` に `-1` を指定すること
【絶対禁止】`_deploy_log/` の既存ファイルを上書きすること
【絶対禁止】`--summary` を省略して承認待ちに入ること

## 実行と検証（あなたがやること）

4ファイルすべて完成したら、以下を**あなた自身が実際に実行して**検証してください。

1. 7つのゲートがどのファイルのどの箇所で実装されているかの対応表を作成して報告
2. `node scripts/04_preflight.js --app={検証用ID}` を実行し、成功を確認
3. `node scripts/05_snapshot_before.js --app={検証用ID}` を実行し、
   `_backup_before/` にフォルダができたことを確認
4. 検証用アプリのJSを意図的に書き換える（`console.log` を1行追加するなど、
   動作が変わるが壊れない変更）
5. `node scripts/06_push_preview.js --app={検証用ID} --source={検証用フォルダ}` を実行
6. まーくんに目視確認を依頼する
   「kintoneで検証用アプリを開き、画面右上に『変更を反映していない設定があります』
   と出ていることと、歯車マーク →『設定』タブ →『JavaScript / CSSでカスタマイズ』で
   ファイル名と並び順が正しいことを確認してください」
7. `node scripts/07_deploy.js --app={検証用ID} --confirm={検証用ID}` を実行
8. Gate 7 の照合結果を報告

## ロールバックの実地検証（省略禁止）

上記に続けて、**戻せることを実際に確認してください。**

1. `_backup_before/{日付}_{検証用フォルダ}/` を `--source` に指定して
   `06_push_preview.js` を実行
2. まーくんに目視確認を依頼
3. `07_deploy.js` を実行
4. 運用環境から取得し直し、**MD5が退避時のものと一致すること**を確認
5. `_deploy_log/` に2回分の記録が残っていることを確認
6. 結果を報告する

## ゲートの故意破壊テスト（省略禁止）

ゲートが本当に効くことを確認します。以下を実行し、**すべて中止されること**を確認してください。

1. `--confirm` に間違ったIDを渡して `07_deploy.js` を実行 → Gate 5 で中止されるか
2. `_backup_before/` の当日フォルダを一時的に別名にして `06_push_preview.js` を実行
   → Gate 2 で中止されるか（確認後、必ず名前を元に戻すこと）
3. 構文エラーのあるJSを `--source` に置いて `06_push_preview.js` を実行
   → Gate 4 で中止されるか（確認後、必ず正しいJSに戻すこと）

【重要】このテストで一時的にファイルを動かした場合、必ず元の状態に戻し、
`git status` がきれいであることを確認してください。
