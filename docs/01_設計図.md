## 1. 目的とスコープ

### 1-1. 目的

1. kintone全アプリのJS/CSSカスタマイズコードを、Gitで版管理する
2. 「誰かがkintone管理画面で直接JSを差し替えた」場合に、それを自動検知できる状態にする
3. デプロイ前の本番コードを必ず退避し、いつでも元に戻せる状態を常に維持する
4. アプリ一覧の取得・フォルダ構成の生成・バックアップの実行を自動化し、手作業を極小化する
5. iPad / Androidから操作を完結できるようにする（PCを開かなくても実行できる）

### 1-2. スコープに含むもの

- アプリ設定のうち「JavaScript / CSSでカスタマイズ」の内容（PC用・モバイル用の両方）
- ファイル指定（アップロード方式）およびURL指定の両方の記録
- ファイルの適用順序、適用スコープ（ALL / ADMIN / NONE）、リビジョン番号
- 上記のバックアップ、差分検知、デプロイ、ロールバック

### 1-3. スコープに含まないもの（意図的に除外）

| 項目 | 理由と代替手段 |
| --- | --- |
| レコードデータ本体 | 既存のGAS＋Googleドライブ方式（_backup_config.json方式）を継続する。二重管理を避ける |
| 添付ファイル | 同上 |
| フィールド定義・フォーム設定 | 第2段階の課題とする。今回はコードのみに絞ることでリスクを限定する |
| プラグイン設定 | プラグインはバイナリ（zip）であり、Git管理の恩恵が薄い |
| Azure Functions のコード | 既存の `irohamie/iroha-functions` リポジトリで管理済み |
| ホームページ | 既存の `irohamie/iroha-web` リポジトリで管理済み |
| GASのコード | 将来的にclaspでの管理を検討するが、今回は対象外 |

## 3. 認証方式の設計（最重要・過去の説明を訂正）

### 3-1. 訂正事項

この会話の初期に「APIトークンに『アプリ管理』権限を追加すれば取得できる」と説明しましたが、これは**誤りである可能性が高い**ため設計を変更します。

kintoneのAPIは大きく2種類に分かれます。

| API種別 | 例 | APIトークン認証 |
| --- | --- | --- |
| レコードAPI | `/k/v1/records.json` | 使える |
| アプリ設定API | `/k/v1/app/customize.json`、`/k/v1/preview/app/deploy.json`、`/k/v1/apps` | **使えない（パスワード認証またはセッション認証が必要）** |

既存のGASバックアップ（`processBackup`）がAPIトークンで動いているのは、レコードAPIしか使っていないためです。今回はアプリ設定APIを使うので、**認証方式そのものを変える必要があります**。

【Phase 0で必ず実測検証すること】上記は設計上の前提です。Sonnetは実装前に `scripts/01_auth_check.js` で両方式を試し、実際にどちらが通るかをログに記録してから先へ進んでください。前提が外れていた場合は、この文書を先に更新してください。

### 3-2. 採用する認証方式

**パスワード認証（`X-Cybozu-Authorization` ヘッダ）** を採用します。

```
X-Cybozu-Authorization: <base64( "ユーザー名:パスワード" )>
```

### 3-3. 専用の自動化用kintoneユーザーを作る

まーくん個人のログインアカウントを使わず、**自動化専用のkintoneユーザーを1つ新規作成**します。

理由：
1. 万一資格情報が漏れた場合、そのユーザーだけを無効化すれば被害を止められる
2. kintoneの更新履歴に「誰が変更したか」が自動化ユーザー名で残り、人の操作と区別できる
3. 権限を必要最小限（対象アプリのアプリ管理権限のみ）に絞れる

制約：
- **2要素認証を有効にしたユーザーではパスワード認証APIが通りません。** 自動化用ユーザーは2要素認証をオフにする代わりに、極めて強いランダムパスワード（32文字以上）を設定し、GitHub Secretsのみに保管します
- Basic認証（IPアドレス制限やセキュアアクセス）がドメイン単位で有効な場合、追加ヘッダが必要になります。Phase 0で確認します

### 3-4. 資格情報の保管場所

| 保管先 | 用途 | 保管するもの |
| --- | --- | --- |
| GitHub Secrets | GitHub Actionsからの実行時 | `KINTONE_BASE_URL` / `KINTONE_USERNAME` / `KINTONE_PASSWORD` |
| ローカルの `.env`（Git管理外） | 手元での実行時 | 同上 |
| GitHub PAT | Git操作用 | `GH_TOKEN`（GitHub Actions内では自動発行の `GITHUB_TOKEN` を使うため不要） |

【禁止】資格情報をコード本体、`apps.json`、コミットメッセージ、ログ出力に書くこと。
【必須】`.gitignore` に `.env` を必ず含めること。

### 4-2. manifest.json の役割（設計上の要点）

kintoneのカスタマイズは「ファイルの中身」だけでは復元できません。以下の情報が失われると復元不能になります。

- **適用順序**：JSは登録順に実行されるため、順序が変わると動作が壊れる
- **適用スコープ**：`ALL`（全員） / `ADMIN`（アプリ管理者のみ） / `NONE`（適用しない）
- **URL指定の項目**：外部CDN（SortableJS等）を参照している行は、ファイルとしては存在しない
- **PC用とモバイル用の区別**：同名ファイルが両方に登録されている場合がある
- **リビジョン番号**：後述の楽観ロックに使う

そのため、これらを `manifest.json` に必ず保存します。

```json
{
  "appId": "228",
  "appName": "タイムカード管理",
  "scope": "ALL",
  "revision": "12",
  "pulledAt": "2026-07-28T07:00:00+09:00",
  "desktop": {
    "js": [
      { "order": 1, "type": "URL", "url": "https://cdn.example.com/Sortable.min.js" },
      { "order": 2, "type": "FILE", "path": "desktop/js/houmon_dashboard.js", "name": "houmon_dashboard.js", "size": 137216, "md5": "…" }
    ],
    "css": []
  },
  "mobile": { "js": [], "css": [] }
}
```

## 5. config/apps.json の設計

`GET /k/v1/apps` の結果から自動生成します。人が手で書くのは `enabled` と `note` の2列だけです。

```json
{
  "generatedAt": "2026-07-28T07:00:00+09:00",
  "baseUrl": "https://iroha-mie.cybozu.com",
  "apps": [
    {
      "appId": "228",
      "name": "タイムカード管理",
      "folder": "App228_タイムカード管理",
      "spaceId": null,
      "enabled": true,
      "note": ""
    }
  ]
}
```

### 5-1. enabled フラグの意味

- `true` … バックアップ・差分検知・デプロイの対象
- `false` … 一覧には載るが、何もしない

初期状態では下記8アプリのみ `true`、それ以外は全て `false` で生成します。
段落的に対象を広げる際は、この `enabled` を `true` に変えるだけで済みます（フォルダは自動生成されます）。

初期の有効アプリ：`10` / `42` / `207` / `219` / `225` / `227` / `228` / `231`

### 5-2. folder名の生成ルール（自動）

kintoneのアプリ名には絵文字や記号が含まれるため、フォルダ名は下記の規則で自動生成します。

1. `App` + アプリID + `_` を先頭に付ける
2. アプリ名の先頭の絵文字・記号は除去する（既存JSの `appNameSort` が扱っている絵文字始まりのアプリ名に対応）
3. `/ \ : * ? " < > |` および制御文字は `_` に置換する
4. 前後の空白は除去、連続する空白は `_` に置換する
5. 結果が空になった場合は `App{ID}_noname` とする
6. 既に別名のフォルダが存在する場合は、**新規作成せず既存フォルダ名を維持し、`apps.json` の `folder` にその既存名を書き込む**（フォルダのリネームによる履歴断絶を防ぐ）

【重要】ルール6により、既に手で作った8フォルダ（`App10_利用希望調査` など）はkintone上の正式名と多少ずれていても、そのまま維持されます。正式名は `apps.json` の `name` に記録されるため情報は失われません。

## 6. 使用するkintone API

| # | 用途 | メソッド・パス | 種別 |
| --- | --- | --- | --- |
| A | アプリ一覧取得 | `GET /k/v1/apps.json` | 読み取り |
| B | 運用環境のカスタマイズ設定取得 | `GET /k/v1/app/customize.json?app={id}` | 読み取り |
| C | テスト環境のカスタマイズ設定取得 | `GET /k/v1/preview/app/customize.json?app={id}` | 読み取り |
| D | ファイル本体のダウンロード | `GET /k/v1/file.json?fileKey={key}` | 読み取り |
| E | ファイルのアップロード | `POST /k/v1/file.json`（multipart） | 書き込み（kintone設定には影響しない） |
| F | テスト環境のカスタマイズ設定更新 | `PUT /k/v1/preview/app/customize.json` | **書き込み（テスト環境のみ）** |
| G | 運用環境への反映 | `POST /k/v1/preview/app/deploy.json` | **書き込み（本番に影響）** |
| H | 反映状況の確認 | `GET /k/v1/preview/app/deploy.json?apps[0]={id}` | 読み取り |

### 6-1. 危険度の区分

- A〜D、H：**完全に安全**。既存の設定・データを一切変更しない
- E：kintoneの一時領域にファイルを置くだけ。アプリ設定は変わらない。未使用のfileKeyは一定期間後に自動破棄される
- F：**テスト環境（動作テスト環境）のみ**が変わる。運用環境は無変更のまま。kintone管理画面上で「変更内容を確認できる状態」になる
- G：**運用環境が実際に書き換わる**。ここが唯一の本当に危険な操作

## 7. 安全性設計

### 7-1. 最大の落とし穴：PUT は「全置き換え」である

`PUT /k/v1/preview/app/customize.json` は、送信した内容で**カスタマイズ設定を丸ごと置き換えます**。部分更新ではありません。

例：あるアプリに3つのJSが登録されている状態で、1つだけを送信すると、**残り2つは黙って消えます**。エラーも警告も出ません。

対策：
1. PUTの直前に必ずBまたはCで現状を取得し、**全ファイルを列挙した完全なリクエストを組み立てる**
2. `manifest.json` に記録された順序を厳守する
3. ファイル数が減る変更は、明示的な `--allow-remove` オプションなしには実行しない（Gate 3）

### 7-2. 二番目の落とし穴：他人の未反映変更を巻き込む

kintoneの「動作テスト環境」は共有です。もし誰かが管理画面でフィールド追加などを行い、まだ「アプリを更新」していない状態のときに `deploy.json` を叩くと、**その人の作業途中の変更も一緒に本番へ反映されてしまいます**。

対策（事前検査 = preflight）：
1. B（運用環境）とC（テスト環境）を両方取得し、**完全に一致していること**を確認する
2. 一致しない場合は「他者の未反映変更あり」と判断し、**処理を中止して人に報告する**
3. これを `scripts/04_preflight.js` として独立させ、デプロイ系スクリプトの先頭で必ず呼ぶ

### 7-3. 三番目の落とし穴：ファイルの切り詰め（過去の実例）

過去に `board.js` が 137KB → 118KB に切り詰められた事故があります。モバイルブラウザ経由のアップロードで発生しました。

対策：
1. ダウンロード時、`customize.json` が返す `size` と実際に保存されたバイト数を突き合わせる。不一致なら即エラー
2. すべてのファイルのMD5ハッシュを `manifest.json` に記録する
3. アップロード後、テスト環境から**取得し直して**MD5を再計算し、送信前と一致することを確認する（Gate 6）
4. 運用環境へ反映後も同様に取得し直して確認する（Gate 7）
5. 人への報告時は、必ずファイル名・バイト数・MD5を明記する

### 7-4. 楽観ロック（revision）の活用

`customize.json` の取得結果には `revision` が含まれます。PUTおよびdeployに同じ `revision` を渡すと、その間に誰かが設定を変更していた場合はkintone側がエラーを返して処理を止めてくれます。

【必須】PUTとdeployには常に `revision` を明示指定すること。`-1`（チェック無効）を指定してはいけません。

### 7-5. デプロイの7つのゲート

`scripts/07_deploy.js` は、下記すべてを通過しない限りdeployを実行してはいけません。

| Gate | 内容 | 失敗時の挙動 |
| --- | --- | --- |
| 1 | preflight：運用環境とテスト環境が一致している | 中止して報告 |
| 2 | 当日分の `_backup_before/` スナップショットが存在し、コミット済みである | 中止して報告 |
| 3 | 送信するファイル数が現行の本番ファイル数を下回らない（下回る場合は `--allow-remove` が必要） | 中止して報告 |
| 4 | 対象の全JSファイルが構文チェック（`node --check` 相当）を通過している | 中止して報告 |
| 5 | 人による明示確認が済んでいる（`--confirm=App228` のようにアプリIDを手入力させる） | 中止して報告 |
| 6 | PUT後、テスト環境から再取得したファイルのMD5が送信前と一致する | deployせず中止して報告 |
| 7 | deploy後、運用環境から再取得したファイルのMD5が一致する | 不一致を報告し、ロールバック手順を提示 |

### 7-6. ロールバックの設計

kintoneには**JSカスタマイズの「前のバージョンに戻す」機能はありません**。戻せるかどうかは、こちら側で取ったバックアップだけが頼りです。

戻す経路は2つ用意します。

**経路1：`_backup_before/` から戻す（第一手段）**

```
_backup_before/
└── 20260728_App228_タイムカード管理/
    ├── manifest.json
    ├── desktop/js/houmon_dashboard.js
    └── mobile/js/
```

デプロイ直前の本番の状態が、そのままの形で入っています。`06_push_preview.js` と `07_deploy.js` にこのフォルダを入力として渡せば、そのまま復元できます。

**経路2：Gitの履歴から戻す（第二手段）**

`git log` で過去のコミットを辿り、任意時点のコードを取り出せます。`_backup_before/` が壊れた場合の保険です。

【禁止】`_backup_before/` および `_deploy_log/` の中身を削除・上書きすること。これらは追記専用です。

## 8. 実装フェーズ（この順序を守る）

| Phase | 内容 | kintoneへの書き込み | 完了条件 |
| --- | --- | --- | --- |
| 0 | 自動化用ユーザー作成、認証方式の実測検証 | なし | `01_auth_check.js` が成功する |
| 1 | アプリ一覧の自動取得、`apps.json` 生成 | なし | 全アプリが `apps.json` に載る |
| 2 | 全有効アプリのJS/CSS一括取得と初回コミット | なし | 8アプリ分のコードとmanifestがコミットされる |
| 3 | 差分検知の自動化（GitHub Actions 毎日実行） | なし | 毎日自動でコミットが積まれる |
| 4 | 検証用アプリでのデプロイ手順の確立 | **テスト用アプリのみ** | 7つのゲートすべてが動作し、ロールバックも成功する |
| 5 | 本番アプリへのデプロイ運用開始 | あり | App228など1アプリで成功 |
| 6 | 対象アプリの段階的拡大（`enabled` を増やす） | あり | 全アプリが対象になる |

【絶対条件】Phase 2の初回コミットが完了するまで、Phase 4以降の書き込み操作を一切行わないこと。バックアップがない状態でのデプロイは、戻せない事故に直結します。

### 8-1. Phase 4の検証用アプリについて

本番アプリで初めてデプロイを試すのは危険です。kintoneで**検証専用のアプリを1つ新規作成**し（例：`テスト_GitHub連携検証`）、そこで7つのゲートとロールバックを一通り確認してください。この検証アプリは `apps.json` に `enabled: true` で登録し、`note` に「検証用・本番運用なし」と記載します。

## 9. 自動化の実行方法（モバイル前提）

まーくんの主な操作端末がiPad / Androidであることを踏まえ、**GitHub Actionsを主実行環境**とします。これにより、PCを開かずスマホのブラウザから操作が完結します。

### 9-1. daily-pull.yml（自動バックアップ）

- トリガー：毎日1回（日本時間の深夜。既存GASバックアップの23時と重ならない時刻にする）＋ `workflow_dispatch`（手動起動ボタン）
- 処理：`02_list_apps.js` → `03_pull_all.js` → 差分があれば自動コミット
- 効果：誰かがkintone管理画面で直接JSを差し替えた場合、翌日のコミット差分として自動的に浮かび上がる

### 9-2. manual-deploy.yml（手動デプロイ）

- トリガー：`workflow_dispatch` のみ（自動実行は絶対にしない）
- 入力欄：対象アプリID、確認文字列、`allow_remove` フラグ
- GitHub Environments の「Required reviewers」機能を使い、**実行前にまーくん自身の承認タップを必須にする**
- 処理：`04_preflight.js` → `05_snapshot_before.js` → コミット → `06_push_preview.js` → `07_deploy.js`

【設計意図】承認ゲートをGitHub側の機能として持たせることで、「うっかり実行」が構造的に起きなくなります。スマホから承認ボタンを押す操作が、そのまま「まーくんの最終確認」になります。

5. 資格情報をコード・ログ・コミットメッセージに残すこと
6. deploy処理を自動トリガー（スケジュール実行やpush連動）にすること
7. アプリフォルダのリネーム（履歴が断絶する）
8. 既存のGAS＋Driveレコードバックアップの設定変更（このプロジェクトとは独立に動かし続ける）
