# iroha-kintone 手順書

この文書は `docs/01_設計図.md` に基づく実作業手順です。Phase 0から順に実行し、前のPhaseが完了するまで次に進まないでください。

## Phase 0：自動化用ユーザーの作成と認証方式の検証

書き込み操作は一切ありません。

### 0-1. kintoneに自動化専用ユーザーを作る（人の作業）

1. スマホまたはPCのブラウザで `https://iroha-mie.cybozu.com` にログインします
2. 画面右上の歯車マーク（設定）をタップします
3. メニューの中から「cybozu.com共通管理」をタップします
4. 左側メニューの「ユーザー」→「組織／ユーザー」をタップします
5. 画面上部の「ユーザーを追加する」ボタンをタップします
6. 以下を入力します
   - 表示名：`GitHub連携（自動）`
   - ログイン名：`github-bot`
   - パスワード：32文字以上のランダムな文字列（後述の生成方法を参照）
   - メールアドレス：空欄で構いません
7. 「保存」をタップします
8. パスワードを、この後GitHub Secretsに登録するまでの間だけ、スマホのメモアプリなどに一時保管します

**パスワードの作り方**：`https://passwordsgenerator.net` などを使うか、下記のコマンドをClaudeに実行させて生成します。
```
openssl rand -base64 32
```

### 0-2. 2要素認証がオフであることを確認する（人の作業）

1. cybozu.com共通管理の「ログイン」→「2要素認証」を開きます
2. 「全ユーザーに2要素認証を必須にする」がオンになっていないことを確認します
3. もしオンになっている場合、このユーザーだけ除外する設定にするか、OAuth方式への設計変更が必要です。その場合はまーくんに報告して指示を待ってください

### 0-3. 対象8アプリのアプリ管理権限を付与する（人の作業）

対象アプリ：10 / 42 / 207 / 219 / 225 / 227 / 228 / 231

各アプリについて以下を行います。

1. kintoneのポータル画面から対象のアプリを開きます
2. 画面右上の歯車マーク（アプリの設定）をタップします
3. 「設定」タブをタップします
4. 「アクセス権」の欄にある「アプリ」をタップします
5. 「ユーザー／組織／グループを追加」の欄で `GitHub連携（自動）` を検索して選択します
6. その行の「アプリ管理」のチェックボックスをオンにします
7. 「レコード閲覧」「レコード追加」「レコード編集」「レコード削除」「ファイル読み込み」「ファイル書き出し」は**すべてオフのまま**にします（コード管理にはアプリ管理権限だけで足ります）
8. 画面右下の「保存」をタップします
9. 画面右上に出る「アプリを更新」ボタンをタップします
10. 確認ダイアログで「更新」をタップします

【注意】手順9の「アプリを更新」を忘れると権限が反映されません。8アプリすべてで実施してください。

### 0-4. GitHub Secretsに資格情報を登録する（人の作業）

1. ブラウザで `https://github.com/irohamie/iroha-kintone` を開きます
2. 画面上部のタブから「Settings」をタップします（歯車マーク）
3. 左側メニューを下にスクロールし、「Secrets and variables」をタップして展開します
4. 「Actions」をタップします
5. 緑色の「New repository secret」ボタンをタップします
6. Name欄に `KINTONE_BASE_URL`、Secret欄に `https://iroha-mie.cybozu.com` を入力し、「Add secret」をタップします
7. 同じ手順を繰り返して、以下2つも登録します
   - Name：`KINTONE_USERNAME` / Secret：`github-bot`
   - Name：`KINTONE_PASSWORD` / Secret：手順0-1で作ったパスワード
8. 3つのSecretが一覧に並んでいることを確認します

【確認】登録後、Secretの中身は二度と表示されません（GitHubの仕様）。まーくんのメモ側に控えを残すか、忘れた場合はkintone側でパスワードを再設定して再登録します。

### 0-5. 認証方式の実測検証（Sonnetの作業）

`scripts/lib/kintone.js` と `scripts/01_auth_check.js` を作成し、実行します。

`01_auth_check.js` の仕様：

| 項目 | 内容 |
| --- | --- |
| 入力 | 環境変数 `KINTONE_BASE_URL` / `KINTONE_USERNAME` / `KINTONE_PASSWORD` |
| 処理1 | `GET /k/v1/apps.json?limit=1` をパスワード認証で叩き、HTTPステータスとレスポンス構造を記録 |
| 処理2 | `GET /k/v1/app/customize.json?app=228` をパスワード認証で叩き、同様に記録 |
| 処理3 | `GET /k/v1/preview/app/customize.json?app=228` を叩き、同様に記録 |
| 出力 | 各処理の成否を日本語で標準出力に表示。失敗時はkintoneが返したエラーコードとメッセージをそのまま表示 |
| 禁止 | 書き込み系APIを一切呼ばないこと。パスワードを出力しないこと |

【完了条件】処理1〜3のすべてがHTTP 200を返すこと。1つでも失敗したら、エラー内容をまーくんに報告して指示を待ってください。

## Phase 1：アプリ一覧の自動取得

書き込み操作はありません。

### 1-1. 02_list_apps.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 処理1 | `GET /k/v1/apps.json` を `limit=100` / `offset` でページングし、全アプリを取得する |

4. 8アプリの `name` が、kintone上の実際のアプリ名と一致していることを確認します。ずれていた場合は、`folder` 名は変えずに `note` にメモを追記します

## Phase 2：全コードの初回バックアップ

**このPhaseの完了が、以降すべての書き込み操作の前提条件です。**
書き込み操作はありません。

### 2-1. 03_pull_all.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 処理1 | `config/apps.json` の `enabled: true` のアプリを対象にループする |
| 処理2 | 各アプリについて `GET /k/v1/app/customize.json?app={id}`（運用環境）を取得する |
| 処理3 | `desktop.js` / `desktop.css` / `mobile.js` / `mobile.css` の4配列を、**配列の順序を保ったまま**処理する |
| 処理4 | `type: "FILE"` の項目は `GET /k/v1/file.json?fileKey={key}` で本体を取得し、`{folder}/desktop/js/{name}` 等に保存する |
| 処理5 | `type: "URL"` の項目はファイル保存せず、manifestにURLのみ記録する |
| 処理6 | 保存後、実際のバイト数がcustomize.jsonの `size` と一致するか検証する。不一致なら**そのアプリの処理を中止**し、エラーとして記録する |
| 処理7 | 各ファイルのMD5を計算し、manifestに記録する |
| 処理8 | `{folder}/manifest.json` を設計図4-2の形式で書き出す |
| 処理9 | 全アプリの処理結果（アプリ名・ファイル名・バイト数・MD5・成否）を表形式で日本語出力する |
| 同名衝突 | PC用とモバイル用に同名ファイルがある場合、フォルダが分かれているため衝突しない。同一フォルダ内で同名が2回出た場合は `{name}_2.js` のように連番を付け、manifestに実際のパスを記録する |
| 禁止 | 書き込み系APIを呼ぶこと。`size` 不一致を無視して先に進むこと |

### 2-2. 初回コミット（Sonnetの作業）

1. `git add -A` で全ファイルをステージする
2. コミットメッセージ：`初回バックアップ：8アプリのJS/CSSを取得（Phase 2）`
3. `git push` する

### 2-3. 初回コミット後の目視確認（人の作業）

1. GitHubで `irohamie/iroha-kintone` を開きます
2. 各アプリフォルダを順にタップし、JSファイルが入っていることを確認します
3. 特に `App228_タイムカード管理/desktop/js/` の中身を開き、`houmon_dashboard.js` などのコードが途中で切れていないことを目で確認します（末尾が `})();` のように正しく閉じているか）
4. `manifest.json` を開き、ファイルサイズが極端に小さくないことを確認します

【重要】ここで「ファイルが1つも取れていないアプリ」があった場合、そのアプリはURL指定方式（GitHub Raw参照など）を使っている可能性があります。その場合はmanifestのURL欄を確認し、`note` に記録してください。

## Phase 3：差分検知の自動化

書き込み操作はありません。

### 3-1. daily-pull.yml の仕様（Sonnetの作業）

```
トリガー：
  - schedule：日本時間の午前4時（既存GASの23時バックアップと重複しない時刻）
  - workflow_dispatch：手動起動用

手順：
  1. リポジトリをチェックアウト
  2. Node.js をセットアップ
  3. 02_list_apps.js を実行
  4. 03_pull_all.js を実行
  5. git diff で差分があるか判定
  6. 差分があれば「自動バックアップ：{日付} 変更検知」というメッセージでコミット・push
  7. 差分がなければ何もせず正常終了
  8. 実行日が月初（1日）なら、有効な各アプリに monthly-{YYYY-MM}-App{ID} タグを作成しpush
  9. 実行日が1月1日なら、有効な各アプリに yearly-{YYYY}-App{ID} タグも作成しpush
  10. エラー時はワークフローを失敗させる（GitHubからメール通知が届く）

環境変数：GitHub Secrets の3つを参照
権限：contents: write
```

【設計意図】月次・年次タグは「削除しない目印」であり、Gitのコミット自体は無期限にすべて残る。既存のGAS＋Driveレコードバックアップとは異なり、古いバックアップを消す処理は一切行わない（設計図 7-7 参照）。

### 3-2. 手動起動の方法（人の作業・スマホから可能）

1. ブラウザで `https://github.com/irohamie/iroha-kintone` を開きます
2. 上部タブの「Actions」をタップします
3. 左側の一覧から「daily-pull」をタップします
4. 右側に出る「Run workflow」ボタンをタップします
5. ブランチが `main` になっていることを確認し、緑色の「Run workflow」をタップします
6. 数十秒後にページを再読み込みすると、実行結果（緑のチェックまたは赤い印）が表示されます

## Phase 4：検証用アプリでのデプロイ手順の確立

**ここから初めてkintoneへの書き込みが発生します。対象は検証用アプリのみです。**

### 4-1. 検証用アプリを作る（人の作業）

1. kintoneのポータル画面で「アプリをつくる」をタップします
2. 「はじめから作成」を選びます
3. アプリ名に `テスト_GitHub連携検証` と入力します
4. 適当な文字列フィールドを1つ配置して「アプリを作成」をタップします
5. 作成後、歯車マーク →「設定」タブ →「JavaScript / CSSでカスタマイズ」を開きます
6. 「PC用のJavaScriptファイル」に、テスト用の短いJSファイルを2つアップロードします（順序の維持を検証するため、必ず2つ以上）
7. 「保存」→「アプリを更新」をタップします
8. Phase 0-3と同じ手順で `GitHub連携（自動）` にアプリ管理権限を付与します
9. アプリIDを確認します（URLの `?app=` の後の数字）

### 4-2. apps.jsonへの登録（Sonnetの作業）

`02_list_apps.js` を再実行し、検証用アプリを `enabled: true`、`note` に `検証用・本番運用なし` として登録します。

### 4-3. 04_preflight.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 引数 | `--app={アプリID}` |
| 処理1 | 運用環境 `GET /k/v1/app/customize.json` を取得 |
| 処理2 | テスト環境 `GET /k/v1/preview/app/customize.json` を取得 |
| 処理3 | 両者のscope・ファイル配列（type / name / url / size）を比較する |
| 処理4 | 完全一致なら「未反映の変更なし。デプロイ可」と出力し終了コード0 |
| 処理5 | 不一致なら差分内容を日本語で表示し、「他者による未反映の変更があるため中止します」と出力して終了コード1 |
| 禁止 | 書き込み系APIを呼ぶこと |

### 4-4. 05_snapshot_before.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 引数 | `--app={アプリID}` |
| 処理1 | `04_preflight.js` を内部で呼び、失敗したら中止する |
| 処理2 | 運用環境の現行コードを `03_pull_all.js` と同じロジックで取得する |
| 処理3 | `_backup_before/{YYYYMMDD}_{folder}/` に保存する（manifest.jsonも含む） |
| 処理4 | 同名フォルダが既に存在する場合は `_2` `_3` と連番を付け、**既存を絶対に上書きしない** |
| 処理5 | `git add` してコミット・pushする。メッセージ：`デプロイ前退避：{アプリ名}（App{ID}） {日付}` |
| 出力 | 保存したパス、ファイル名、バイト数、MD5の一覧 |
| 完了条件 | pushが成功していること。push失敗時は後続のデプロイを行わせない |

### 4-5. 06_push_preview.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 引数 | `--app={アプリID}` / `--source={フォルダパス}` / `--allow-remove`（任意） |
| 処理1 | preflightを内部で呼び、失敗したら中止 |
| 処理2 | 当日の `_backup_before/` スナップショットの存在を確認。無ければ中止（Gate 2） |
| 処理3 | `--source` のmanifest.jsonを読み、送信するファイル一覧と順序を組み立てる |
| 処理4 | 全JSファイルに構文チェックを行う。1つでも失敗したら中止（Gate 4） |
| 処理5 | 現行本番のファイル数と送信ファイル数を比較。減る場合は `--allow-remove` が無ければ中止（Gate 3） |
| 処理6 | 各ファイルを `POST /k/v1/file.json` でアップロードし、fileKeyを得る |
| 処理7 | `PUT /k/v1/preview/app/customize.json` に、scope・4配列すべて・`revision` を明示して送信する |
| 処理8 | `GET /k/v1/preview/app/customize.json` で再取得し、各ファイルを `file.json` でダウンロードしてMD5を再計算。送信前と一致しなければエラー報告（Gate 6） |
| 出力 | 送信前後のファイル名・バイト数・MD5の対照表 |
| 禁止 | `deploy.json` を呼ぶこと（このスクリプトはテスト環境までで止まる） |
| 禁止 | `revision: -1` を指定すること |

### 4-6. テスト環境での目視確認（人の作業）

`06_push_preview.js` の実行後、必ずここを通します。

1. kintoneで対象アプリを開きます
2. 画面右上に「変更を反映していない設定があります」という表示が出ていることを確認します
3. 歯車マーク →「設定」タブ →「JavaScript / CSSでカスタマイズ」を開きます
4. ファイル名と並び順が意図通りであることを確認します
5. ファイル数が想定通りであることを確認します（減っていないか）

【重要】この時点で運用環境は一切変わっていません。おかしいと感じたら、kintone画面右上の「変更を中止」をタップすれば、テスト環境の変更が破棄されて元に戻ります。この「変更を中止」が最初の安全弁です。

### 4-7. 07_deploy.js の仕様（Sonnetの作業）

| 項目 | 内容 |
| --- | --- |
| 引数 | `--app={アプリID}` / `--confirm={アプリID}`（必須） |
| 処理1 | `--confirm` の値が `--app` と一致することを確認。不一致なら中止（Gate 5） |
| 処理2 | 当日の `_backup_before/` スナップショットの存在とコミット済みを確認（Gate 2） |
| 処理3 | `POST /k/v1/preview/app/deploy.json` に `app` と `revision` を指定して送信 |
| 処理4 | `GET /k/v1/preview/app/deploy.json` を数秒間隔でポーリングし、`status` が `SUCCESS` になるまで待つ。`FAIL` なら即報告 |
| 処理5 | 運用環境 `GET /k/v1/app/customize.json` を取得し、全ファイルのMD5を再計算して照合（Gate 7） |
| 処理6 | `_deploy_log/{YYYYMMDD_HHMMSS}_App{ID}.md` に、実行日時・対象・送信前後のMD5・結果を追記形式で記録し、コミット・push |
| 出力 | 成否、照合結果、`_deploy_log` のパス |
| 禁止 | `revision: -1` を指定すること。preflight・Gate 2をスキップすること |

### 4-8. ロールバックの実地検証（Sonnetと人の共同作業）

Phase 4は「戻せることを確かめる」ことが目的です。以下を実際にやってください。

1. 検証用アプリに、意図的に壊れた（動作が変わる）JSをデプロイする
2. kintoneでアプリを開き、動作が変わったことを確認する
3. `_backup_before/{日付}_{検証用アプリフォルダ}/` を `--source` に指定して `06_push_preview.js` を実行する
4. 4-6の目視確認を行う
5. `07_deploy.js` を実行する
6. kintoneでアプリを開き、**元の動作に戻っていること**を確認する
7. `_deploy_log/` に2回分の記録が残っていることを確認する

【完了条件】手順6で元に戻ることを目で確認できたら、Phase 4は完了です。ここが確認できるまで、本番アプリへのデプロイは行いません。

## Phase 5：本番アプリへのデプロイ運用開始

### 5-1. manual-deploy.yml の仕様（Sonnetの作業）

```
トリガー：workflow_dispatch のみ（scheduleとpushトリガーは絶対に付けない）

入力欄（inputs）：
  - app_id：対象アプリID（必須、文字列）
  - confirm：確認用にアプリIDを再入力（必須、文字列）
  - source：送信元フォルダパス（省略時はアプリ本体フォルダ）
  - allow_remove：ファイル数が減ることを許可（既定 false）

environment：production
  ※ GitHub の Settings → Environments で "production" を作成し、
    Required reviewers に irohamie を設定すること。
    これにより実行前に承認タップが必須になる。

手順：
  1. チェックアウト
  2. Node.js セットアップ
  3. 04_preflight.js --app={app_id}
  4. 05_snapshot_before.js --app={app_id}
  5. 06_push_preview.js --app={app_id} --source={source} [--allow-remove]
  6. 一時停止して手動承認を待つ（Environments の承認ゲート）
  7. 07_deploy.js --app={app_id} --confirm={confirm}
  8. ログをコミット・push

権限：contents: write
```

### 5-2. Environments の承認設定（人の作業）

1. `https://github.com/irohamie/iroha-kintone` を開きます
2. 上部タブの「Settings」をタップします
3. 左側メニューの「Environments」をタップします
4. 「New environment」ボタンをタップします
5. Name欄に `production` と入力し、「Configure environment」をタップします
6. 「Required reviewers」のチェックボックスをオンにします
7. 現れた入力欄に `irohamie` と入力して選択します
8. 「Save protection rules」をタップします

これで、デプロイ実行時にスマホへ承認依頼が届き、まーくんがタップするまで処理が止まります。

### 5-3. 最初の本番デプロイ（人の作業）

最初の1本は、影響範囲が小さいアプリを選んでください。推奨は `App219_ポータル` ではなく、**単独で動いていて他アプリから参照されていないアプリ**です。App231（担当表）やApp225（3町月次報告）が候補になります。

1. Actionsタブ →「manual-deploy」→「Run workflow」
2. app_id と confirm に同じアプリIDを入力
3. 「Run workflow」をタップ
4. preflight・snapshot・push_previewが進む
5. kintoneを開いて4-6の目視確認を行う
6. GitHubに戻り、承認依頼の「Review deployments」→「Approve and deploy」をタップ
7. 完了後、kintoneでアプリの動作を確認する

## Phase 6：対象アプリの段階的拡大

1. `config/apps.json` の `enabled` を `false` から `true` に変更する対象を決める（一度に5アプリ程度まで）
2. `03_pull_all.js` を実行し、新規対象のコードを取得する
3. Phase 2-3と同じ目視確認を行う
4. コミット・push
5. 問題がなければ次のグループへ

【推奨】全アプリを一度に有効化しないこと。取得エラーが出たアプリの原因切り分けが難しくなります。
