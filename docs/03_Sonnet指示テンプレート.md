# Sonnet指示テンプレートとコード生成規約

この文書は、Sonnetに実装を依頼するときの指示文と、守らせるコード生成ルールをまとめたものです。

---

## 1. 毎回冒頭に貼る共通前提（必須）

Sonnetは会話をまたいで記憶を持たないため、**新しいチャットを始めるたびに以下をそのまま貼ってください。**

```
【前提】
NPO法人いろ葉のkintone（iroha-mie.cybozu.com）のJS/CSSコードを、
GitHubリポジトリ irohamie/iroha-kintone でGit管理するプロジェクトです。

以下3つの文書を読み込んでから作業を始めてください。
- docs/01_設計図.md
- docs/02_手順書.md
- docs/03_Sonnet指示テンプレート.md

【絶対に守ること】
1. Phase 2（初回バックアップ）完了前に、kintoneへの書き込み系APIを一切呼ばない
2. PUT/deployに revision: -1 を指定しない
3. preflightを飛ばしてdeployしない
4. _backup_before/ と _deploy_log/ の中身を削除・上書きしない
5. 資格情報をコード・ログ・コミットメッセージに出力しない
6. アプリフォルダをリネームしない
7. deployを自動トリガー（scheduleやpush連動）にしない

【今回の作業】
（ここにPhase番号と具体的な依頼を書く）
```

## 2. コード生成規約（まーくんの標準ルール）

### 2-1. 完全版出力の原則

- コードは常に**完全版・省略なし**で出力すること
- 「（以下省略）」「（変更なし）」「// 既存のコードはそのまま」といった省略表記は禁止
- 一部だけを直す場合でも、そのファイル全体を最初から最後まで出力すること
- 指示された箇所以外の既存コードを、要約・短縮・削除しないこと

### 2-2. 4ブロック分割アペンド方式

1回の出力で巨大なコードを書き込むと途中で切れるため、以下の手順を必ず踏むこと。

```
手順1：コードを4つ程度のブロックに分割する
手順2：cat でブロック1を新規作成（> でリダイレクト）
手順3：cat でブロック2〜4を順に追記（>> でリダイレクト）
手順4：node --check で構文チェック
手順5：カスタム検証（後述）を実行
手順6：ファイルサイズとMD5を人に報告
```

コマンド例：
```bash
cat > scripts/03_pull_all.js << 'BLOCK1_EOF'
（ブロック1の内容）
BLOCK1_EOF

cat >> scripts/03_pull_all.js << 'BLOCK2_EOF'
（ブロック2の内容）
BLOCK2_EOF

（ブロック3、4も同様）

node --check scripts/03_pull_all.js && echo "構文OK"
wc -c scripts/03_pull_all.js
md5sum scripts/03_pull_all.js
```

### 2-3. カスタム検証（生成後に必ず実行）

生成したコードについて、以下を自動的に検証し、結果を人に報告すること。

| # | 検証内容 | 判定方法 |
| --- | --- | --- |
| 1 | 構文が正しいか | `node --check` が成功する |
| 2 | 省略表記が混入していないか | ファイル内を `以下省略` `変更なし` `省略` `...` `TODO` で検索し、0件であること |
| 3 | 関数の欠落がないか | 定義したはずの関数名をすべて `grep -c` で数え、宣言と呼び出しの対応を確認する |
| 4 | ファイルが切り詰められていないか | `wc -c` のバイト数を報告し、末尾の数行を `tail -5` で表示して閉じ括弧を確認する |
| 5 | 禁止APIが混入していないか | `deploy.json` を呼ぶ箇所が、`07_deploy.js` 以外に存在しないことを確認する |
| 6 | revision の扱い | `revision` を `-1` で送っている箇所が0件であることを確認する |
| 7 | 資格情報の漏洩 | `console.log` の引数に `PASSWORD` `password` `token` を含む箇所が0件であることを確認する |

検証結果は次の形式で報告すること。

```
【検証結果】scripts/03_pull_all.js
構文チェック：OK
省略表記の混入：0件
定義関数：8個（すべて呼び出しあり）
ファイルサイズ：14,208 バイト
MD5：a1b2c3...
末尾3行：（表示）
禁止API混入：なし
revision: -1 の使用：0件
資格情報の出力：なし
```

### 2-4. 過去の事故を踏まえた必須事項

| 事故 | 必須対策 |
| --- | --- |
| board.js が 137KB → 118KB に切り詰められた | ファイル出力後、必ずバイト数とMD5を明記して報告する |
| GitHub Web UIのドラッグ＆ドロップで関数が消失した | GitHubへのファイル投入はWeb UIのD&Dを使わず、必ずgitコマンド（またはGitHub Actions）経由で行う |
| モバイルD&Dが動作しない | 生成するコードがブラウザ側UIを含む場合、SortableJSは `forceFallback: true` と `touch-action: none` を併用する |

### 2-5. 説明の書き方

- 説明は超丁寧に、ボタンひとつまで詳しく書くこと
- 「歯車マークをタップ」「画面右下の保存をタップ」のように、実際の画面上の位置と操作を明記すること
- 出力が長くなる場合は複数回に分けること。回数をケチらないこと
- 謝罪は不要。欠陥を悔いる必要もない。訂正が必要なときは、事実だけを簡潔に述べて修正案を出すこと
- ❌マークは使わないこと

## 3. Phase別の指示文テンプレート

以下をコピーして、共通前提の「【今回の作業】」欄に貼ってください。

### Phase 0（認証検証）

```
Phase 0 の 0-5 を実施してください。

1. scripts/lib/kintone.js を作成
   - kintone REST API のラッパー
   - パスワード認証（X-Cybozu-Authorization ヘッダ）を使う
   - 環境変数 KINTONE_BASE_URL / KINTONE_USERNAME / KINTONE_PASSWORD を読む
   - get(path, params) / postFile(filePath) / put(path, body) / post(path, body) を提供
   - エラー時はkintoneが返したエラーコードとメッセージをそのまま投げる
   - パスワードを絶対にログ出力しない

2. scripts/01_auth_check.js を作成
   - 手順書 0-5 の仕様どおり、読み取り3種を試して結果を日本語表示
   - 書き込み系APIは呼ばない

3. .gitignore を作成（.env、node_modules を除外）

4. 4ブロック分割アペンド方式で出力し、カスタム検証7項目を実行して報告
```

### Phase 1（アプリ一覧取得）

```
Phase 1 の 1-1 を実施してください。

scripts/02_list_apps.js を作成し、手順書 1-1 の仕様に従ってください。

特に注意：
- 既存の config/apps.json の enabled と note を必ず引き継ぐこと
- 既存フォルダがある場合、フォルダ名を維持し apps.json の folder にその名前を書くこと
- 初回のみ 10/42/207/219/225/227/228/231 を enabled: true にすること
- ページング（limit=100, offset）で全件取得すること

4ブロック分割アペンド方式で出力し、カスタム検証7項目を実行して報告してください。
```

### Phase 2（初回バックアップ）

```
Phase 2 の 2-1 を実施してください。

scripts/lib/verify.js と scripts/03_pull_all.js を作成し、手順書 2-1 の仕様に従ってください。

特に注意：
- customize.json の size と実際の保存バイト数が一致しない場合、そのアプリの処理を中止してエラー記録すること（無視して進めない）
- desktop/mobile × js/css の4配列すべてを、配列の順序を保ったまま manifest.json に記録すること
- type: "URL" の項目はファイル保存せず、URLのみ manifest に記録すること
- revision を manifest に記録すること
- 全ファイルのMD5を manifest に記録すること
- 書き込み系APIは一切呼ばないこと

実行後、全アプリの結果を「アプリ名／ファイル名／バイト数／MD5／成否」の表形式で報告してください。
```

### Phase 3（差分検知の自動化）

```
Phase 3 の 3-1 を実施してください。

.github/workflows/daily-pull.yml を作成し、手順書 3-1 の仕様に従ってください。

特に注意：
- schedule は日本時間の午前4時（cron は UTC なので 19時前日 = "0 19 * * *"）
- workflow_dispatch も付けること
- permissions: contents: write を明記すること
- Secrets の3つを env で渡すこと
- 差分がない場合は commit せず正常終了させること
- deploy 系スクリプトは絶対に呼ばないこと
```

### Phase 4（デプロイ手順の確立）

```
Phase 4 の 4-3 から 4-7 を実施してください。

作成するファイル：
- scripts/04_preflight.js（手順書 4-3）
- scripts/05_snapshot_before.js（手順書 4-4）
- scripts/06_push_preview.js（手順書 4-5）
- scripts/07_deploy.js（手順書 4-7）

7つのゲート（設計図 7-5）をすべて実装してください。
1つでもゲートを省略したら、この作業は失敗とみなします。

特に注意：
- PUT は全置き換えである。4配列すべてを完全に列挙して送ること
- revision を明示指定し、-1 は使わないこと
- 06_push_preview.js は deploy.json を呼んではいけない
- 07_deploy.js は --confirm が --app と一致しないと動いてはいけない
- Gate 6 と Gate 7 では、実際にファイルをダウンロードし直してMD5を再計算すること（size比較だけでは不十分）

1ファイルずつ、4ブロック分割アペンド方式で出力してください。
4ファイルを一度に出力しようとしないこと。
```

### Phase 5（本番デプロイ運用）

```
Phase 5 の 5-1 を実施してください。

.github/workflows/manual-deploy.yml を作成し、手順書 5-1 の仕様に従ってください。

特に注意：
- トリガーは workflow_dispatch のみ。schedule と push は絶対に付けない
- environment: production を指定すること（承認ゲートのため）
- inputs は app_id / confirm / source / allow_remove の4つ
- 07_deploy.js は承認ゲートの後に実行されるステップに置くこと
```

## 4. Sonnetが判断に迷ったときの原則

1. **迷ったら止める。** 書き込み系の操作で判断がつかない場合、実行せずまーくんに質問する
2. **推測でAPIを叩かない。** 仕様が不明なAPIは、まず読み取りで挙動を確認してから使う
3. **設計図と矛盾する実装をしそうになったら、実装ではなく設計図の更新を提案する**
4. **エラーを飲み込まない。** try-catchで握りつぶさず、必ず内容を表示して処理を止める
5. **「動いたからよし」としない。** バイト数とMD5で裏を取るまで完了と報告しない

## 5. まーくん側の確認チェックリスト（各Phase共通）

Sonnetの作業が終わったら、以下をスマホから確認してください。

1. GitHubの「Code」タブで、対象ファイルが存在するか
2. ファイルをタップして開き、末尾が正しく閉じているか（`}` や `})();` で終わっているか）
3. Sonnetが報告したバイト数と、GitHub上に表示されるサイズが一致しているか
4. 「Commits」タブで、コミットメッセージが日本語で内容を表しているか
5. `_backup_before/` の中身が減っていないか
